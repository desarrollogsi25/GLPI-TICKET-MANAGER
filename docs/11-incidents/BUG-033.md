# BUG-033 — Los tests E2E de Playwright no se verificaban estáticamente en CI

> **Control Documental ISO 9001 / ISO 27001**  
> **Código:** DOC-11-INC-BUG-033 | **Versión:** 1.0.0 | **Fecha:** 2026-10-22 | **Autor:** GLPI Ticket Manager Team

## 1. Resumen Ejecutivo

- **ID del Incidente:** BUG-033
- **Fecha y Hora de Inicio (UTC):** 2026-10-22 (detectado al cerrar BUG-032)
- **Fecha y Hora de Resolución (UTC):** 2026-10-22
- **Severidad:** P3 — Bajo (defecto preventivo de cadena de calidad; no hubo impacto
  en producción)
- **Servicios Afectados:** Job `frontend` de CI (`.github/workflows/ci.yml`), suite E2E
  de Playwright
- **Lead del Incidente:** GLPI Ticket Manager Team

**Síntoma:** el job `frontend` de CI ejecutaba `pnpm typecheck` (`tsc --noEmit`) sobre
un `tsconfig.json` cuyo `include` era `["src", "vite.config.ts"]`. **Los 25 specs E2E
de `frontend/tests/e2e/` quedaban fuera del typecheck.** Un error de tipos en un
spec (por ejemplo, un `expect` mal tipado o un payload de API con la forma equivocada)
no se detectaba en el job de verificación estática: sólo se manifestaba en tiempo de
ejecución dentro del job `e2e`, como un fallo de test mucho más caro de diagnosticar
y directamente atribuido a la funcionalidad bajo prueba.

El hueco se hizo visible al cerrar [BUG-032](BUG-032.md): la regresión que protege el
Kanban se implementa como un spec E2E nuevo (`kanban-polling.spec.ts`), y ese spec
**debía** quedar cubierto por el typecheck para que un error de tipos no pasara
desapercibido hasta la noche de CI.

## 2. Impacto en el Negocio y Usuarios

- **Usuarios impactados:** ninguno directamente (no hubo defecto en producción).
- **Impacto en el equipo:** coste de diagnóstico. Los fallos de tipos en los specs
  aparecían como fallos E2E ambiguos («el botón no estaba», «el elemento no se
  encontró») en lugar de como errores de compilación claros, en el job más lento de
  la tubería (25 min de presupuesto).
- **Riesgo latente:** un spec con tipos rotos puede seguir compilando y ejecutándose
  (Playwright transpila con esbuild, que **descarta** la información de tipos sin
  comprobarlos), de modo que un assert mal escrito puede «pasar» sin comprobar lo que
  el autor cree que comprueba.

## 4. Análisis de Causa Raíz

### 4.1 Causa raíz — el `include` del `tsconfig.json` excluía el árbol de pruebas

```jsonc
// frontend/tsconfig.json (ANTES)
{
  "compilerOptions": { /* ... */ },
  "include": ["src", "vite.config.ts"]   // ← `tests/` nunca se analizaba
}
```

El `include` se configuró cuando el proyecto sólo tenía código de aplicación en
`src/`. Cuando se añadió el árbol `tests/e2e/`, nadie amplió el `include`: el
typecheck siguió verificando la aplicación, pero **nunca verificó los tests**.

### 4.2 Causa contribuyente — Playwright transpila sin comprobar tipos

El runner de Playwright compila los specs con esbuild, que elimina las anotaciones de
tipo **sin verificarlas**. Un spec con un error de tipos no falla al compilar: se
ejecuta como si fuera correcto. El único tipo de error que sí aborta la ejecución es
el de los tipos de las APIs del propio Playwright en tiempo de compilación de TS, lo
que ocurre únicamente si el spec se incluye en un proyecto de `tsc`.

### 4.3 Causa contribuyente — el job `frontend` y el job `e2e` no comparten el typecheck

`.github/workflows/ci.yml` tiene dos jobs distintos:

| Job | Qué hace | ¿Verifica los specs? |
|---|---|---|
| `frontend` | `pnpm typecheck` + `pnpm build` | **No** (por el `include` restringido) |
| `e2e` | Suite completa de Playwright sobre el stack real | Los ejecuta, pero **no** comprueba sus tipos |

El resultado era que el **único** punto de control sobre los specs era la ejecución en
tiempo de prueba: demasiado tarde y demasiado caro.

## 4.1bis. Alcance real del hueco

- **25 specs** (`*.spec.ts`) + `global-setup.ts` + `support/ticket-fixtures.ts`
  = **27 archivos TypeScript** en `frontend/tests/e2e/`.
- **0 de esos 27 archivos** entraban en el programa de `tsc` que CI ejecutaba.

## 5. Evidencia de Reproducción

### 5.1 Estado anterior — los specs no entran en el typecheck

```bash
$ cat frontend/tsconfig.json | grep include
"include": ["src", "vite.config.ts"]

$ cd frontend && pnpm typecheck
$ tsc --noEmit
# (exit 0 — pero ningún archivo bajo tests/ fue analizado)
```

Comprobación de que el árbol de tests quedaba realmente fuera del proyecto:

```bash
$ cd frontend && npx tsc --noEmit --listFiles -p tsconfig.old.json | grep -c "tests/e2e"
0        # ← 0 specs analizados por el typecheck de CI (include anterior, medido)
```

### 5.2 Comprobación previa al cambio — los specs compilan sin errores

Para no romper el CI con una corrección a ciegas, se verificó **antes** de tocar el
`tsconfig.json` que los specs existentes (incluido el nuevo) analizan sin un solo
error:

```bash
$ cd frontend && npx tsc --noEmit -p tsconfig.check.json   # include: ["src","tests","vite.config.ts"]
EXIT=0
# (sin salida: ningún error de tipos)
```

### 5.3 Estado posterior

```bash
$ cd frontend && pnpm typecheck
$ tsc --noEmit
TYPECHECK_EXIT=0

$ cd frontend && npx tsc --noEmit --listFiles | grep -c "tests/e2e"
27        # ← 27 archivos (25 specs + global-setup.ts + support/ticket-fixtures.ts)
```

## 6. Corrección Aplicada

Un único cambio, en `frontend/tsconfig.json`:

```jsonc
// frontend/tsconfig.json (DESPUÉS)
{
  "compilerOptions": { /* ... */ },
  "include": ["src", "tests", "vite.config.ts"]
}
```

Efectos:

1. `pnpm typecheck` (job `frontend` de CI) y `pnpm build` analizan ahora **también**
   los specs de Playwright.
2. Un error de tipos en un spec falla en el job **rápido** y barato, con el mensaje
   exacto de TypeScript, en lugar de fallar en el job `e2e` como un fallo de
   functionality ambiguo.
3. El job `e2e` no cambia: sigue ejecutando la suite completa, ahora sobre specs
  -tipados.

No se modificó `.github/workflows/ci.yml`: los jobs existentes ya ejecutan
`pnpm typecheck` y la suite completa de Playwright, de modo que el hueco se cierra
**sin** tocar la tubería.

## 9. Lecciones Aprendidas

- **La cobertura de verificación estática es una decisión de configuración, no de
  intención.** `tsconfig.json` es un contrato: si un directorio del repositorio no
  está en el `include`, ese directorio no existe a efectos de verificación.
- **Un job de CI puede «cubrir» un directorio sin verificarlo.** La suite E2E se
  ejecutaba entera en CI, lo que daba una falsa sensación de cobertura; lo que faltaba
  era la verificación estática de esos mismos archivos.
- **Un test nuevo es el momento de cerrar el hueco.** La regresión de BUG-032
  introducía un spec nuevo; exigir que ese spec pase el typecheck evitó que la
  cobertura del proyecto se degradara en silencio.
