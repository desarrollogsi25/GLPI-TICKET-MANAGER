# BUG-032 — Inestabilidad 429 en el Kanban y confirmación de estado contra GLPI

> **Control Documental ISO 9001 / ISO 27001**
> **Código:** DOC-11-INC-BUG-032 | **Versión:** 1.0.0 | **Fecha:** 2026-10-22 | **Autor:** GLPI Ticket Manager Team

## 1. Resumen Ejecutivo

- **ID del Incidente:** BUG-032 (tickets H-32 y refuerzo de H-31)
- **Fecha y Hora de Inicio (UTC):** 2026-10-14 (primeras quejas de la mesa de ayuda),
  reproducido de forma determinista el 2026-10-22
- **Fecha y Hora de Resolución (UTC):** 2026-10-22
- **Severidad:** P2 — Alto (degradación visible del Kanban; el usuario ve el tablero
  desactualizarse y avisos de error; no hay pérdida de datos)
- **Servicios Afectados:** Kanban y cola de grupo (`GET /api/tickets/by-group`), página de
  cola (`/queue`), dashboard (`/dashboard`), política de rate limiting `Expensive`
- **Lead del Incidente:** GLPI Ticket Manager Team

**Síntoma reportado por el técnico:** el tablero Kanban «se congela» o «se actualiza a
saltos», aparecen avisos de error «Demasiadas solicitudes» y el contador de tickets en
la cola deja de moverse aunque otros técnicos estén trabajando.

El incidente tiene **dos facetas** que se corrigieron en el mismo cambio:

1. **H-32 — el origen del 429.** El cliente pedía la cola del grupo **cada 1,5 s**
   (40 peticiones/minuto) contra un endpoint cuyo *bucket* de tokens permite
   **20 peticiones/minuto** en producción. El servidor respondía `429` a un tercio de
   las peticiones; el tablero se quedaba sin datos frescos y el técnico veía errores.
2. **H-31 (refuerzo) — la confirmación de estado.** El backend confirmaba las
   transiciones de estado leyendo el **modelo de lectura en MariaDB**, no a **GLPI**.
   Con un modelo de lectura desfasado, el API publicaba un evento «estado cambiado»
   que GLPI nunca había aplicado.

## 2. Impacto en el Negocio y Usuarios

- **Usuarios impactados:** todos los técnicos y supervisores con el Kanban abierto
  (el Kanban es la pantalla principal de la mesa de ayuda).
- **Operaciones degradadas:** la cola del grupo no se refrescaba de forma confiable;
  reintentos manuales de «Asignarme» fallaban con `409` porque el estado en pantalla
  era viejo.
- **Pérdida o inconsistencia de datos:** **No**. Ninguna escritura se perdió: el
  `429` es una lectura rechazada y las escrituras jamais fueron bloqueadas por el
  limitador (sólo las lecturas de la cola de grupo usan la política `Expensive`).
- **Efecto secundario del diseño:** al recibir `429` sin cabecera `Retry-After` y con
  cuerpo vacío, el cliente no tenía forma de saber cuándo reintentar y el
  `QueryClient` reintentaba a ciegas, agravando el consumo de tokens.

## 4. Análisis de Causa Raíz

### 4.1 Causa raíz de H-32 — el cliente pedía el doble de lo que el servidor permite

`GET /api/tickets/by-group` está protegido por la política `Expensive`:

```csharp
// src/GlpiTicketManager.Api/Program.cs (producción, appsettings.json)
"RateLimiting": {
  "Expensive": { "PermitLimit": 20, "Window": 60, "TokensPerPeriod": 1, "ReplenishmentPeriod": 3 }
}
```

Es decir, **20 tokens de capacidad** y **1 token cada 3 s** ⇒ **20 peticiones/minuto**
sostenibles por usuario.

El cliente pedía **40 peticiones/minuto**:

```typescript
// frontend/src/features/tickets/Kanban.tsx (ANTES)
const queueQuery = useGroupQueueQuery(currentGroupId, 1500)   // ← 1,5 s
```

Medición con navegador real (Chromium), API con la **cuota de producción**, 180 s de
observación sobre `/kanban`:

| | Peticiones | `200` | `429` | Separación entre llamadas | SignalR |
|---|---:|---:|---:|---|---|
| **ANTES** | **120** | 80 | **40** | ≈ 1,7 s | `connected` todo el tiempo |
| **DESPUÉS** | **1** | 1 | **0** | — | `connected` todo el tiempo |

Es decir: el servidor contestaba correctamente a un cliente que pedía el doble de lo
sostenible. **La cuota de producción no se tocó** (requisito explícito): el arreglo es
del cliente.

### 4.2 Causa contribuyente — un segundo poller invisible en las opciones de la query

El `refetchInterval` de TanStack Query era el fuente visible del problema, pero
`Kanban.tsx` tenía además su propio temporizador:

```typescript
// frontend/src/features/tickets/Kanban.tsx (ANTES)
useEffect(() => {
  if (activeTab !== 'queue') return
  const interval = setInterval(() => {
    void queueQuery.refetch()          // ← ignora por completo el estado de la conexión
  }, 30000)
  return () => clearInterval(interval)
}, [activeTab, queueQuery])
```

Este temporizador no aparece en ninguna opción de la query, no se puede desactivar
desde la configuración y seguía golpeando el endpoint protegido durante toda la
sesión. Se descubrió **empíricamente**, no por lectura del código: la traza de pila
del `queryFn` apuntaba a `Kanban.tsx:536`, no al temporizador de TanStack Query
(cambiar `QUEUE_FALLBACK_POLL_MS` a 7 s **no** cambió el periodo observado de 30 s).

### 4.3 Causa contribuyente — el `429` no era accionable

La respuesta `429` del API era un cuerpo vacío sin `Retry-After`:

```
HTTP/1.1 429 Too Many Requests
Content-Length: 0
Date: ...
Server: Kestrel
```

El cliente no podía saber cuándo reintentar, y el `QueryClient` reintentaba a ciegas.

### 4.4 Causa raíz secundaria (H-31) — la confirmación se leía del modelo de lectura

`TicketService.ResolveAsync` y `UpdateStatusAsync` confirmaban la transición leyendo
`ITicketRepository.GetByIdAsync`, es decir, el **modelo de lectura en MariaDB**. Ese
modelo puede estar desfasado respecto de GLPI (lecturas concurrentes, caché del
proveedor, reglas de workflow que rechazan la transición). Consecuencia: el API podía
emitir un evento `TicketStatusChanged` con un estado que **GLPI nunca aplicó**.

### 4.5 Causa contribuyente — las pruebas no veían el problema

- El entorno de desarrollo (`appsettings.Development.json`) sube `ExpensiveTokenLimit`
  a 200, de modo que **el `429` no se reproducía en el stack de desarrollo**.
- Los tests de integración nunca ejecutaron el `QueryClient` del frontend: el
  poller estaba en el cliente y ninguna prueba de backend podía detectarlo.

## 6. Corrección Aplicada

### 6.1 Frontend — SignalR primario con fallback condicional (H-32)

1. **`useGroupQueueQuery(groupId, options)`** (`frontend/src/hooks/useTickets.ts`):
   la cadencia de polling vive **en un único sitio** y es **condicional**:

   ```typescript
   refetchInterval: () => {
     if (!sessionValid) return false
     if (connectionState === 'connected') return false   // SignalR es el canal primario
     if (fallbackIntervalMs === false) return false
     return fallbackIntervalMs                           // 30 s sólo si el hub está caído
   },
   refetchIntervalInBackground: false,
   ```

   `QUEUE_FALLBACK_POLL_MS = 30_000` ⇒ **2 peticiones/minuto** en el peor caso.
2. **`Kanban.tsx`**: se elimina el `setInterval` heredado de 30 s. No queda **ningún**
   temporizador de polling en el Kanban.
3. **`useRealtimeTicketHub.ts`**: se distingue `'reconnecting'` de `'connecting'` y, en
   `onreconnected`, se vuelve a suscribir al grupo y se invalidan
   `byGroupQueue` / `tickets.all` (al reconectar se perdió la pertenencia al grupo).
4. **Sin reintentos a ciegas**: `QueryClient` no reintenta ante `429` ni ante `4xx`
   (`frontend/src/main.tsx`); el `apiClient` respeta `Retry-After` y avisa una sola vez
   cada 10 s; `ProtectedRoute` y `useSessionValidity` detectan el token caducado en
   lugar de insistir con peticiones que serían rechazadas.
5. **`ConnectionIndicator`**: estado `reconnecting` visible para el técnico.

### 6.2 Backend — el `429` pasa a ser accionable

`options.OnRejected` de la política `Expensive` responde ahora con `Retry-After` y un
cuerpo `ProblemDetails` (RFC 7807) que incluye `retryAfterSeconds`.

### 6.3 Backend — la confirmación de estado se lee de GLPI (H-31)

1. Nuevo `IGlpiApiClient.GetTicketStateAsync(ticketId)` →
   `GET /apirest.php/Ticket/{id}` (GLPI 11 devuelve `id`, `name`, `status`,
   `solvedate`, `closedate`, `date_mod`, `is_deleted`).
2. `ResolveAsync` y `UpdateStatusAsync` **releen el estado desde GLPI** después de
   escribir y **publican el estado que GLPI confirma**, no el que el código quiso
   escribir. Si GLPI rechaza la transición, se registra una advertencia y el evento
   refleja el estado real.
3. Un fallo de la relectura se **registra pero nunca deshace** una escritura que ya
   tuvo éxito (resiliencia, no ocultamiento de errores).

### 6.4 Frontend — el cierre de sesión cierra el socket **antes** de revocar el token

Eliminando el polling agresivo, el tráfico del Kanban pasó a depender por completo de
SignalR. Eso volvió visible una condición de carrera que hasta entonces pasaba
inapercibida: **el flujo de logout revocaba el JWT mientras el handshake del WebSocket
seguía en vuelo**. El servidor respondía `401` a ese *upgrade* y el navegador
registraba en consola:

```
WebSocket connection to 'ws://localhost:5173/hubs/tickets?...&access_token=<JWT revocado>'
failed: HTTP Authentication failed; no valid credentials available
```

Es un error que el usuario no ha provocado: el propio cliente se está desvalidando
mientras su propia conexión se negocia.

**Orden corregido del cierre de sesión** (`frontend/src/lib/api/auth.ts`):

```typescript
export async function logout(): Promise<void> {
  await stopRealtimeConnection()   // 1. cerrar el socket
  await apiClient.post('/auth/logout') // 2. revocar el token
}
```

`stopRealtimeConnection()` (`frontend/src/hooks/useRealtimeTicketHub.ts`) **espera a
que el handshake pendiente se resuelva** antes de cerrar el socket: abortar un
WebSocket a mitad de *upgrade* produciría otro mensaje de consola
(«WebSocket is closed before the connection was established») y no resolvería nada.
Con el orden corregido, el servidor nunca llega a ver un token revocado.

## 9. Lecciones Aprendidas

- **Un `429` es una respuesta correcta a un cliente incorrecto.** La primera hipótesis
  —«hay que subir el límite del servidor»— era errónea: la cuota de producción es la
  regla de negocio y el defecto estaba en el cliente.
- **El entorno de desarrollo escondía el defecto.** `appsettings.Development.json`
  multiplica la cuota por diez; sin una instancia en `Production` el problema no se
  reproduce. El incidente sólo se closes con una comparativa BEFORE/AFTER
  determinista (contenedor recién reiniciado ⇒ *bucket* en el mismo estado).
- **Un temporizador puede vivir fuera de la configuración de la librería.** El
  `refetchInterval` de TanStack Query era una de las dos fuentes de polling; la otra
  era un `setInterval` imperceptible en las opciones. La traza de pila del `queryFn`
  fue la que reveló la segunda.
- **«Conectar» no es lo mismo que «estar suscrito».** Al reconectar, el cliente
  pierde la pertenencia al grupo del hub; sin restaurarla, el tablero queda mudo
  aunque la conexión figure como establecida.
- **Confirmar contra el sistema de registro, no contra el modelo de lectura.** El
  modelo de lectura en MariaDB puede estar desfasado; la verdad del estado está en
  GLPI.
- **Cerrar una sesión es una operación con orden.** Socket primero, token después.
  Revocar el token mientras la conexión se negocia produce un `401` que el navegador
  reporta como error de consola, y la condición de carrera existía **antes** de este
  arreglo: la línea base en `HEAD` ya fallaba 2 de 6 veces. Lo que hizo el arreglo
  H-32 fue llevarla al 100 %, al multiplicar por diez la dependencia del socket.
  Un defecto latente puede parecer nuevo si aparece justo después de otro cambio;
  la única forma de distinguirlo es la línea base medida.
