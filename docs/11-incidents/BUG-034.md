# BUG-034 — El flujo Pendiente → Replanificar devolvía 409 contradictorio y no reanudaba el ticket

> **Control Documental ISO 9001 / ISO 27001**  
> **Código:** DOC-11-INC-BUG-034 | **Versión:** 1.0.0 | **Fecha:** 2026-11-06 | **Autor:** GLPI Ticket Manager Team

## 1. Resumen Ejecutivo

- **ID del Incidente:** BUG-034
- **Fecha y Hora de Inicio (UTC):** 2026-11-06 (reporte del usuario sobre el ticket #1032)
- **Fecha y Hora de Resolución (UTC):** 2026-11-06
- **Severidad:** P1 — Alto (bloquea por completo el flujo operativo Pendiente → En proceso desde el Kanban)
- **Servicios Afectados:** API de planificación (`POST /api/tickets/{id}/plan`,
  `PUT /api/tickets/{id}/tasks/{taskId}`), modal de planificación y de reprogramación del
  frontend, columna `Pendiente` del Kanban (escritorio y móvil)
- **Lead del Incidente:** GLPI Ticket Manager Team

**Síntoma:** un ticket en estado `Pendiente` (GLPI 4) con una tarea `TicketTask` propia
ya programada no podía replanificarse. El modal enviaba `POST /api/tickets/{id}/plan`,
la API respondía `409 Conflict` con el detalle genérico «Ya tienes otra tarea programada
durante ese horario» y el frontend, al no recibir un código de error legible, mostraba
además el titular «El ticket ya no está en un estado que permita esta operación». El
técnico veía **dos mensajes contradictorios** y el ticket permanecía en `Pendiente`.
El conflicto reportado no era un solapamiento con otro ticket: era **la propia tarea
del mismo ticket** la que ocupaba el intervalo solicitado.

**Causa raíz:** el endpoint de planificación no distinguía entre «reprogramar la tarea
existente del propio ticket» y «crear una tarea nueva», y el endpoint de reprogramación
rechazaba explícitamente el estado `Pendiente`. El único camino que quedaba abierto era
crear una segunda tarea, que la comprobación de solapamiento volvía a rechazar por
colisionar con la primera. El error se presentaba sin un `code` que el cliente pudiera
interpretar, de modo que la interfaz lo clasificaba como un problema de estado.

## 2. Impacto en el Negocio y Usuarios

- **Bloqueo operativo:** un técnico no podía retomar un ticket pausado conservando su
  planificación. La única salida disponible era resolver el ticket o pedir apoyo a un
  administrador para conciliar GLPI manualmente.
- **Riesgo de duplicados:** la ruta alternativa (crear una tarea nueva) generaba una
  segunda `TicketTask` sobre el mismo ticket, perdiendo la relación entre la
  planificación original y la nueva y ensuciando el historial de GLPI.
- **Pérdida de confianza en la UI:** los dos mensajes simultáneos («estado inválido» y
  «horario ocupado») impedían saber qué corregir. En móvil, donde el modal ocupa la
  pantalla completa, el usuario no disponía de ningún dato para resolver el conflicto.
- **Sin pérdida de datos:** ninguna operación del flujo fallido llegó a escribir en
  GLPI; el 409 se producía antes de cualquier mutación.

## 4. Análisis de Causa Raíz

### 4.1 Causa principal — la tarea propia se contabilizaba como conflicto ajeno

`PlanAsync` comprobaba solapamientos con `HasOverlappingScheduledTaskAsync(..., excludingTaskId: null)`.
Al replanificar un ticket que **ya tenía** una tarea programada, esa misma tarea entraba
en la consulta y el resultado era un 409. El mensaje, además, se redactó para el caso
«otro ticket»:

```csharp
// ANTES
if (await _tickets.HasOverlappingScheduledTaskAsync(userId,
        request.StartAt.UtcDateTime, request.EndAt.UtcDateTime, excludingTaskId: null, ct))
{
    throw new ConflictException("Ya tienes otra tarea programada durante ese horario. Elige otro intervalo.");
}
```

No había forma de saber desde el cliente si el conflicto era la tarea del propio ticket
(que debe reprogramarse) o una tarea de otro ticket (que exige elegir otro horario).

### 4.2 Causa principal — la reprogramación rechazaba el estado Pendiente

`ReplanTaskAsync` abortaba de forma explícita cuando el ticket estaba en `Waiting`:

```csharp
// ANTES
if (state.Status == (int)TicketStatus.Waiting)
    throw new ConflictException("Para salir de Pendiente crea una nueva planificación; GLPI debe confirmar el cambio de estado.");
```

Esa instrucción era incorrecta. El mecanismo nativo de GLPI para salir de `Pendiente`
consiste en actualizar la `TicketTask` con `pending=0` y nuevas fechas: el hook
post-update de GLPI reabre el ticket (`Waiting → Assigned`) y deriva `Planned` de la
tarea `ToDo`. Crear una segunda tarea no era necesario y además chocaba con la tarea
original en la comprobación de solapamiento (causa 4.1).

### 4.3 Causa contribuyente — autorización contra una transición que GLPI no ejecuta

La política de acceso autorizaba `Waiting → Planned` (4 → 3), pero esa transición no
existe en la máquina de estados de GLPI para el técnico: GLPI ejecuta `Waiting →
Assigned` y luego deriva `Planned`. La autorización se evaluaba contra una transición
imposible, de modo que la operación legítima quedaba denegada o, peor, autorizada bajo
un supuesto que nunca se cumplía.

### 4.4 Causa contribuyente — reintento idéntico sin efecto nativo

Una reprogramación con la misma fecha, duración y comentario es un *no-op* para GLPI:
sus hooks no se ejecutan y el ticket no se reanuda. El usuario veía un 200 sin efecto
(o, tras la primera corrección, un 409 genérico). El comportamiento correcto es
rechazarlo de forma explícita con un mensaje que indique qué modificar.

### 4.5 Causa contribuyente — los 409 no llevaban código ni contexto

`GlobalExceptionHandler` sólo serializaba `title` y `detail`. El frontend no podía
distinguir un conflicto de horario de uno de estado, así que mapeaba cualquier 409 al
mensaje genérico «El ticket ya no está en un estado que permita esta operación». Ese
fue el origen de la contradicción visible: el backend informaba de un solapamiento y
la interfaz lo presentaba como un cambio de estado.

### 4.6 Causa contribuyente — el modal no ofrecía información para resolver el conflicto

El diálogo no cargaba las tareas nativas del ticket, no distinguía entre reprogramar
lo existente y crear algo nuevo, no bloqueaba el doble envío y no mostraba los
intervalos ocupados ni una alternativa concreta.

### 4.7 Defecto detectado durante la verificación — columnas unsigned sin CAST

La nueva consulta de conflictos materializaba filas en un `record` con `long` para
`TaskId` y `TicketId`. MariaDB informa `glpi_tickettasks.id` y `tickets_id` (INT
`UNSIGNED`) como `UInt32`, por lo que Dapper no encontraba un constructor compatible y
lanzaba:

```text
System.InvalidOperationException: A parameterless default constructor or one matching
signature (System.UInt32 TaskId, System.UInt32 TicketId, System.DateTime StartUtc,
System.DateTime EndUtc) is required for ...ConflictRow materialization
```

El resultado era un `500 Error inesperado` en **toda** planificación (la consulta se
ejecuta siempre), no sólo en Pendiente. Se detectó en la suite E2E aislada, donde seis
specs quedaron bloqueados en `confirmPlanning`, y se reprodujo contra MariaDB real con
un pequeño cliente Dapper. La corrección aplica `CAST(... AS SIGNED)` en el `SELECT`,
el mismo patrón ya usado en las consultas del watcher de tiempo real.


## 5. Evidencia de Reproducción

Reproducción en Chrome real contra el despliegue LAN, con ticket sintético #1034
(asignado a `tech_dev`, tarea #30 programada y estado 4):

```text
POST /api/tickets/1034/plan  →  409 application/problem+json
{
  "title": "Conflict",
  "detail": "Ya tienes otra tarea programada durante ese horario. Elige otro intervalo."
}

UI:
  toast destructivo: "El ticket ya no está en un estado que permita esta operación"
  alerta del modal:  "Ya tienes otra tarea programada durante ese horario"
  peticiones POST /plan observadas: 1
```

La consulta a las tareas nativas del ticket mostró que la tarea #30 (mismo ticket,
mismo técnico) era la que ocupaba el intervalo solicitado. No existía colisión con
otro ticket ni doble envío del formulario.

## 6. Corrección Aplicada

### 6.1 Backend — adoptar y reprogramar la tarea propia

`PlanAsync` ahora:

1. Carga las tareas nativas del ticket.
2. Si el llamador no pidió explícitamente una tarea nueva (`CreateNewTask = false`,
   valor por defecto), busca una tarea `ToDo` **del mismo técnico y del mismo ticket**
   que solape el intervalo solicitado y la adopta como objetivo de reprogramación.
3. Consulta conflictos con `GetScheduledTaskConflictsAsync`, **excluyendo la tarea
   adoptada**. Si queda algún conflicto, responde `409 schedule_conflict` con los
   intervalos ocupados y un hueco libre sugerido.
4. Con objetivo adoptado, llama a `ReplanTicketTaskAsync` (GLPI `pending=0` + fechas),
   completa la clave de idempotencia, relee la tarea y exige que GLPI confirme el
   estado `3`. Nunca escribe `3` directamente ni crea una segunda tarea.
5. Si el ticket está `Planned` y no hay tarea adoptable, responde `state_conflict`
   indicando que debe reprogramarse la tarea existente.

`CreateNewTask = true` sigue disponible como elección explícita: en ese caso la tarea
propia solapada se reporta como conflicto en lugar de adoptarse, para no duplicarla.

`ReplanTaskAsync` ahora:

- Acepta `Waiting` como estado de origen y autoriza la transición real
  `Waiting → Assigned` (la que GLPI ejecuta), no la imposible `Waiting → Planned`.
- Exige que GLPI confirme `3` tras la reprogramación; si no, responde
  `409 glpi_unconfirmed` con el `taskId` y el estado observado.
- Rechaza un reintento idéntico con `409 no_changes` y un mensaje que explica que GLPI
  sólo reanuda cuando la tarea cambia.
- Distingue `task_modified`, `task_not_editable`, `idempotency_conflict` y
  `state_conflict` con códigos estables.

La consulta de conflictos (`TicketRepository.GetScheduledTaskConflictsAsync`) proyecta
`CAST(tt.id AS SIGNED)` y `CAST(tt.tickets_id AS SIGNED)` para que Dapper materialice
las columnas `UNSIGNED` de MariaDB como `long`.

### 6.2 Contrato de error legible

`ConflictException` transporta `Code` y `Details`; el `ProblemDetails` los expone como
extensiones:

```json
{
  "status": 409,
  "code": "schedule_conflict",
  "detail": "El técnico ya tiene otra tarea programada durante ese horario: ticket #55 (tarea #901): 2026-11-10 09:00 – 10:00 UTC. Elige otro intervalo.",
  "requestedStart": "2026-11-10T09:30:00Z",
  "requestedEnd": "2026-11-10T10:30:00Z",
  "ownTaskId": null,
  "conflicts": [
    { "ticketId": 55, "taskId": 901, "startAt": "2026-11-10T09:00:00Z", "endAt": "2026-11-10T10:00:00Z" }
  ],
  "suggestedStart": "2026-11-10T10:00:00Z"
}
```

Códigos publicados: `schedule_conflict`, `state_conflict`, `task_modified`,
`task_not_editable`, `no_changes`, `idempotency_conflict`, `glpi_unconfirmed`.

### 6.3 Frontend — un modal que explica y resuelve

`PlanTicketDialog` y `ReplanTicketTaskDialog` ahora:

- Cargan las tareas reales de GLPI al abrirse.
- Ofrecen dos modos explícitos: **Reprogramar tarea existente** (por defecto cuando hay
  una tarea `ToDo`) y **Crear tarea nueva**.
- Bloquean el doble envío con una referencia de envío y deshabilitan el botón mientras
  hay una mutación en curso.
- Validan fechas (hueco DST, duración 1 min – 30 días) y detectan localmente el
  *no-op* antes de llamar a la API.
- Muestran el error específico según `code`, conservan los datos introducidos y, ante
  `schedule_conflict`, listan los intervalos ocupados y ofrecen **«Usar horario libre»**
  con el `suggestedStart` y **«Reprogramar mi tarea #N»** cuando la tarea propia es la
  que bloquea.
- Confirman el éxito con un mensaje claro y refrescan Kanban y detalle de inmediato.
- No permiten guardar mientras la lista de tareas GLPI está cargando o falló: muestran
  el error con **Reintentar carga de tareas** y mantienen los campos introducidos. Sin
  esta guarda, un fallo de red transitorio se habría interpretado como «no hay tareas»
  y el modo «crear nueva» habría duplicado el trabajo existente.

## 9. Lecciones Aprendidas

- **Un conflicto debe nombrar su causa.** El mismo código HTTP para «estado incorrecto»
  y «horario ocupado» obligó al cliente a adivinar y produjo un mensaje contradictorio.
  Los códigos estables y el contexto estructurado son parte del contrato, no un extra.
- **Replanificar no es crear.** La tarea nativa es la fuente de verdad del calendario:
  mover la existente conserva el identificador, el historial y la relación con el
  ticket. Crear otra para «salir de Pendiente» era la causa del bloqueo.
- **La máquina de estados de GLPI manda.** La autorización debe evaluarse contra la
  transición que GLPI ejecuta realmente (`Waiting → Assigned` con derivación a
  `Planned`), no contra la transición lógica que el dominio preferiría.
- **Un no-op no reanuda nada.** Los hooks de GLPI se saltan cuando el payload no cambia;
  detectarlo antes de escribir evita respuestas engañosas.
- **MariaDB `UNSIGNED` no es `long`.** Dapper materializa las columnas `INT UNSIGNED`
  como `UInt32`; cualquier `record` posicional con `long` debe leer `CAST(... AS SIGNED)`.
  Las pruebas con repositorios simulados no detectan este desajuste: sólo una consulta
  real o una suite E2E lo revela.
